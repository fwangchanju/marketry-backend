# 결정 기록

이미 논의해서 결론이 난 사안을 적어둔다. 같은 판단을 다시 하기 전에 여기부터 본다.

## 이 문서의 규칙

- 설계·문서 담당 세션만 수정한다. 구현 세션은 읽기만 하고 작업 중 알게 된 것은 PR 설명에 남긴다
- 결정과 그 이유만 적는다. 구현 세부사항(어떤 필드를 추가했고 어떤 제약을 걸었는지)은 적지 않는다.
  그건 코드와 PR에 있다
- 검토했다가 접은 선택지와 접은 이유를 반드시 함께 적는다. 결론만 적으면 나중에 "왜 이렇게 했지?"
  하면서 되돌리게 된다
- 기준은 "다음에 또 설명해야 할 것인가"다. 그게 아니면 적지 않는다

아직 안 한 일은 여기가 아니라 `docs/backlog.md`에 적는다. 이 문서는 이미 결론이 난 것만 다룬다.

> 이전에는 `docs/history.md`가 이 역할이었는데, "중요한 맥락은 계속 추가하라"는 지시를 작업 중인
> 쪽이 수행하면서 구현 세부사항이 계속 쌓여 쓸모가 떨어졌다. 그래서 쓰는 주체를 분리하고, 이름도
> `history`(있었던 일을 다 적는 곳)에서 `decisions`(결정이 아니면 안 적는 곳)로 바꿨다.

# 작업 방식

## 코드를 한 줄씩 확인하는 방식을 그만뒀다

**결정**: 사용자는 코드를 직접 읽지 않는다. 검증은 자동화된 수단(CI·테스트)과 PR 설명으로 한다.

**이유**: 물리적인 시간이 너무 많이 들었다.

**따라오는 것**: 사람 리뷰가 빠진 자리를 자동 검증이 메워야 한다. 그래서 CI·테스트가 "있으면 좋은 것"이
아니라 품질을 보장하는 유일한 수단이 됐다. `docs/rules/process.md`의 "빌드·테스트는 기본 동작"
규칙과 `docs/rules/testing.md`가 전부 여기서 나온다.

## PR은 기능 단위로 나눈다 — 예전에 묶었던 건 배포 때문이었다

**결정**: 기능 하나 = PR 하나. "오늘 한 일 전부"를 한 PR에 묶지 않는다.

**예전 방식과 그 이유**: 여러 작업을 묶어 PR 하나로 올렸다. 표면적으로는 "쓸데없는 커밋·PR이 늘어나는
게 싫어서"였는데, 실제 이유는 따로 있었다. main 병합이 곧 배포였고, 배포하면 서버가 내려갔다.
사용자가 웹을 실제로 쓰고 있으니 PR을 나눌수록 다운타임이 늘어난다. 무의식적으로 배포 횟수를
최적화하고 있었던 것이고 그 자체는 옳은 판단이었다.

그래서 진짜 해법은 PR 개수가 아니라 배포를 떼는 것이었다(아래 항목).

## 병합과 배포를 분리했다

**결정**: main 병합 시 이미지 태그 승격만 하고 배포는 하지 않는다. 배포는 수동으로 원하는 시점에
실행한다.

**이유**: 병합("코드가 확정됐다")과 배포("사용자에게 나갔다")는 원래 별개 개념인데, 붙어 있어서 코드
관리 방식이 배포 사정에 끌려다녔다. 떼면 PR을 자유롭게 나누고 배포는 장 시간을 피해 몰아서 할 수 있다.

**중요 — 승격은 남긴다**: `promote-main` job을 통째로 끄면 안 된다. 그러면 `:main` 태그가 안 만들어져서
나중에 수동 배포할 때 이미지가 없고, 처음부터 다시 빌드하게 된다. 빌드가 두 번 도는 셈이다.
그래서 재태깅(승격) 스텝은 남기고 배포·헬스체크 스텝만 제거했다.

**nginx·renderer에도 똑같이 적용한다**: 이 둘도 main push 시 자동으로 빌드·배포·헬스체크까지
나가고 있었다. `infra/nginx.conf` 한 줄 고친 PR을 장중에 병합하면 nginx가 내려갔다 뜬다
(`deploy-nginx.sh`가 `down` → `up -d`). 규칙을 애플리케이션에만 적용할 이유가 없어서 함께 끈다.

예외 하나 — 프론트 자산 발행(`repository_dispatch`)에 의한 nginx 자동 배포는 남긴다. 프론트
코드는 nginx 이미지 안에 구워지므로 이게 프론트의 유일한 배포 경로다. 여기까지 수동으로 만들면 프론트
배포가 백엔드 레포를 거치는 2단계 작업이 된다.

**접은 선택지**: 무중단 배포(blue-green 등)로 전환하면 다운타임 자체가 사라지지만 개인 프로젝트
규모에 비해 과하다고 보고 접었다. 배포 방식을 크게 바꾸게 되면 그때 다시 검토한다.

## 브랜치 시험 배포를 없애고 롤백으로 대체했다

**결정**: "브랜치를 프로덕션에 띄워보고 괜찮으면 머지"하는 구조를 없앤다. 배포 경로는
`application`(`:main`)과 `rollback`(`:previous`) 둘뿐이고 "Use workflow from"은 항상 main이다.

**예전 구조와 그 이유**: 프론트는 상태가 없어서 "띄웠다 되돌리기"가 공짜다. 백엔드는 DB가 껴 있어서
그게 안 됐고, 그래서 마이그레이션 규칙(선-머지 2단계, 하위호환 추가만)을 만들어 억지로 성립시켰다.

뒤집는 이유 — 그 규칙이 트라이얼을 불필요하게 만든다

순환이 있었다.

> 트라이얼을 하려고 → 마이그레이션 규칙을 만들었는데
> → 그 규칙이 있으면 이미지만 되돌려도 안전해지고
> → 그러면 트라이얼이 굳이 필요 없어진다

마이그레이션 규칙이 트라이얼의 전제였는데, 그 규칙 자체가 롤백을 안전하게 만들어버렸다. 트라이얼이
자기 존재 이유를 스스로 없앤 셈이다.

결과적으로 워크플로가 절반으로 줄고(`:branch-` 태그 체계, 브랜치 분기 로직 제거), 사용자가 고를 것도
하나로 줄어든다. 백엔드 CI/CD가 복잡했던 원인이 이 트라이얼 구조였다.

단, `build` job(브랜치 push 시 `:sha-` 빌드)은 남긴다. 사용자에겐 안 보이지만 승격의 재료이고,
없으면 배포 버튼을 누를 때마다 전체 빌드가 돈다.

## 롤백은 포인터 태그 방식으로 한다

**결정**: `:deployed`(마지막 프로덕션 배포) / `:previous`(그 직전) 두 포인터를 워크플로가 자동으로
관리하고 롤백은 `target=rollback` 하나로 끝낸다.

검토한 대안들

| 방식 | 왜 안 골랐나 |
|---|---|
| Roll forward (문제를 고쳐서 다시 배포) | 고치는 동안 장애가 지속된다. revert PR을 만드는 게 싫어서 지금 구조를 만든 것이기도 하다 |
| 이미지 태그를 매번 찾아 입력 | 사고 났을 때 GHCR을 뒤져 태그를 찾는 것 자체가 부담이다. 예전에 `deploy_ref` 텍스트 입력을 없앤 이유와 같은 문제 |
| Blue-green / canary | 개인 프로젝트 규모에 과하다 |

**포인터 방식을 고른 이유**: `kubectl rollout undo`나 ArgoCD의 "이전 리비전으로" 버튼이 하는 일과
같다. 핵심은 무엇으로 되돌릴지 사람이 찾지 않는다는 것이다. 도구가 직전 것을 기억한다.
새 입력란도 안 생긴다. 이미 있는 `target` 드롭다운에 선택지 하나가 늘 뿐이다.

**이 프로젝트에서 이미지 롤백이 안전한 이유**: 마이그레이션 규칙(하위호환 추가만, 선-머지)이 이미
있어서 스키마가 항상 구버전 코드와 호환된다. 롤 포워드가 권장되는 주된 이유(되돌리면 스키마가 안 맞음)가
여기선 해당하지 않는다.

포인터 방식이 성립하려면 지켜야 하는 불변식

> 서버에 떠 있는 이미지 = `:deployed`

`:previous`는 "직전 배포"가 아니라 "직전에 정상 동작하던 것"이어야 의미가 있다. 이게 깨지면
롤백이 조용히 엉뚱한 곳으로 간다. 검증 과정에서 깨질 수 있는 경로 세 개를 찾았고, 전부 1A 지시서에
조치를 넣었다.

| 깨지는 경로 | 조치 |
|---|---|
| 배포 스크립트가 헬스체크 전에 컨테이너를 교체하므로, 헬스체크 실패 시 서버는 새 이미지인데 `:deployed`는 옛 이미지 → 롤백이 두 단계 전으로 감 | 헬스체크 실패 시 워크플로가 `:deployed`를 자동 재배포해 원상복구하고 실패시킨다 |
| `:main`이 그대로인 상태의 재배포(인프라 스크립트 반영용)에서 포인터를 밀면 `:previous == :deployed`가 되어 롤백이 무력화됨 | 배포한 다이제스트가 기존 `:deployed`와 같으면 포인터를 건드리지 않는다 |
| `:deployed` ↔ `:previous` 맞바꾸기를 태그 두 개 순차 덮어쓰기로 하면 둘 다 같은 이미지를 가리키게 됨 | 먼저 다이제스트를 변수에 고정한 뒤 민다 |

한계 세 가지 (문서에 명시하고 살기로 한 것)
- 롤백은 토글이다. 두 번 누르면 되돌아온다. 두 단계 전으로 가는 수단은 없다. `kubectl rollout
  undo`도 같은 동작이라 그대로 둔다. 대신 `docs/operations.md`에 명시했다
- 롤백 후 `application`을 누르면 사고 낸 이미지가 다시 나간다. 롤백은 `:main`을 바꾸지 않는다.
  revert PR로 `:main`을 갱신하는 것이 정공법이다
- 롤백은 애플리케이션 이미지만 되돌린다. 서버는 배포 시 `git reset --hard origin/main`으로
  스크립트를 가져오므로 `nginx.conf`·`docker-compose.yml`·배포 스크립트는 최신이 유지된다. 인프라
  변경을 되돌리려면 revert PR이 필요하다

포인터는 프로덕션 배포(`application`/`rollback`)에서만 움직인다. 다른 배포 경로를 나중에
추가하더라도 포인터를 건드리게 하면 안 된다. 롤백이 "시험하다 버린 이미지"로 돌아간다.

GHCR 보관 개수를 5 → 20으로 올렸다. 정리 액션은 태그가 붙어 있어도 오래된 것부터 지운다.
"브랜치 작업 → 시험 배포 → 즉시 병합"이 순차적이라 5로 충분했는데, 배포를 병합에서 떼어낸 순간 그
전제가 깨진다. 배포 없이 application PR을 5건 병합하면 `:previous`가 가리키던 버전이 먼저 사라진다.

**부수 효과**: `:deployed`와 `:main`을 비교하면 "병합해놓고 배포를 깜빡했는지"를 바로 알 수 있다.
배포와 병합을 분리하면서 생긴 리스크가 이걸로 해소된다.

## 문서를 쓰는 주체와 코드를 쓰는 주체를 분리했다

**결정**: 문서(`docs/`, `CLAUDE.md`)는 설계·문서 담당 세션이 쓰고, 구현 세션은 읽기만 한다.

이유: 작업 중인 쪽은 자기가 방금 한 일이 다 중요해 보여서 문서에 구현 세부사항을 계속 쌓는다.
실제로 `history.md`가 그렇게 오염됐고, 그때마다 "적지 마라"고 제지하는 것도 번거로웠다. 기록 여부를
판단하는 주체를 작업자와 분리하면 이 문제가 구조적으로 사라진다.

## 지시서(휘발성)와 규칙 문서(영속)를 구분한다

결정: 작업 착수 전에 만드는 지시서는 별도 파일로 두고, 작업이 끝나면 삭제한다.

이유: 이 구분이 없어서 작업 로그가 영속 문서로 흘러들어갔다. 지시서를 따로 만들고 버리면 영속
문서는 깨끗하게 유지된다.

## 리뷰 왕복에 상한을 둔다

결정: PR당 리뷰 왕복 최대 1회. 2회차에도 안 맞으면 리뷰어가 직접 고친다. 지적은 차단/제안으로
구분하고 제안은 그대로 병합한다.

이유: 상한이 없으면 리뷰가 라인바이라인 확인으로 회귀한다. 벗어나려는 그 상태로 돌아가면 의미가
없다.

## 단계를 건너뛰면 되돌리라고 알려준다

결정: 범위와 완료 기준이 정해지지 않은 상태로 코드 작성을 요청받으면, 진행하기 전에 "먼저 정하고
가자"고 제안한다. 사용자가 그대로 진행하라고 하면 진행하되 PR에 절차를 생략했다고 남긴다.

이유: 사용자가 급하거나 귀찮을 때 절차를 건너뛰게 되는데, 그때 같이 대충 넘어가지 않게 하는
장치가 필요하다. 다만 강제하면 규칙 자체가 지워지므로 거절이 아니라 제안이어야 하고 기록은
남겨야 원인 추적이 된다.

# 기술 결정

## `EscalateException`(텔레그램 즉시 알림)을 쓰는 기준

`EscalateException`은 HTTP 500 + 개발자에게 즉시 텔레그램 알림이 나가는 예외다. 아무 500에나
붙이는 게 아니다.

알림이 필요한 케이스는 하나로 수렴한다. 완전한 실시간은 아니더라도, 그 시간대에 맞지 않는 잘못된
데이터가 사용자에게 전달되어 잘못된 판단을 유도할 위험이 있는 경우. 수집기 실패가 대표적이다.
수집이 실패하면 과거 스냅샷이 최신인 것처럼 노출된다.

알림 대상이 아닌 것: 관리자 화면 조작 중 발생하는 오류, 특정 기능이 그 자리에서 동작하지 않는 경우.
사용자가 그 시점에 인지하고 고치면 되는 수준이고 잘못된 데이터로 오판을 유도할 위험이 없다.

`style.md`의 "`IllegalStateException` 직접 사용 금지 → `EscalateException` 사용"은 모든
`IllegalStateException`을 일괄 대체하라는 뜻이 아니라, 위 기준에 해당할 때 그렇게 하라는 뜻이다.
해당하지 않으면 일반 `BusinessException`을 쓴다.

> 어떤 케이스가 알림 대상인지는 코드 패턴이 아니라 판단의 영역이라 `style.md`에 규칙으로 넣지 않고
> 여기에만 적는다.
>
> 현재는 텔레그램으로 개발자에게 직접 보내는 구조인데, 추후 슬랙 등 팀 채널로 옮길 계획이 있어

## `lombok.config`를 둔다 — `@Qualifier`가 조용히 무시되기 때문

**결정**: 레포 루트에 `lombok.config`를 두고 `@Qualifier`를 복사 대상으로 등록한다.

```
lombok.copyableAnnotations += org.springframework.beans.factory.annotation.Qualifier
```

**이유**: `@RequiredArgsConstructor`가 만드는 생성자에는 필드의 애노테이션이 복사되지 않는다.
Lombok은 `lombok.copyableAnnotations`에 등록된 것만 파라미터로 옮긴다. 생성자 주입에서 Spring은
파라미터의 애노테이션만 보므로, 필드에 붙인 `@Qualifier`는 읽히지도 않고 오류도 안 난다.

**이게 왜 위험한가**: 이 프로젝트의 `RestClient`는 `@Primary` 빈이 하나 있고 용도별 빈이 여럿이다.
`@Qualifier`가 무시되면 전부 `@Primary`로 주입되면서 기동도 성공하고 테스트도 통과한다. 실제로
2단계에서 렌더러 타임아웃이 90초 대신 10초로 주입되는 일이 있었고, 배포 후 일일 리포트가 안 나가야
알 수 있는 상태였다. 바이트코드(`javap -v`로 `RuntimeVisibleParameterAnnotations` 확인)로만 잡힌다.

**접은 선택지**: 필드명을 빈 이름과 맞춰 파라미터명 매칭에 기대는 방법. 성립하지 않는다 —
Spring은 `@Primary`를 파라미터명 매칭보다 먼저 적용한다(`DefaultListableBeanFactory
.determineAutowireCandidate`). `@Primary` 빈이 있는 한 계속 그쪽이 선택된다.

## catch-all 예외 핸들러가 걸러야 하는 것

`GlobalExceptionHandler`의 `@ExceptionHandler(Exception.class)`는 MVC 내장 예외를 다시 던져야
한다. 안 그러면 정상적인 4xx가 500이 되고 요청 하나하나가 텔레그램 알림이 된다. 인증 실패
401·403이 `ResponseStatusException`으로 나가고 사이트가 공개돼 있으므로, 봇 스캔만으로도 채널이 죽는다.

`ErrorResponse` 구현 여부만으로 판단하면 안 된다. `ResponseEntityExceptionHandler`가 다루는
예외 중 아래 넷은 `ErrorResponse`가 아니라서 catch-all에 걸린다.

- `TypeMismatchException` (→ `MethodArgumentTypeMismatchException`, `ConversionNotSupportedException`)
- `HttpMessageNotReadableException`
- `HttpMessageNotWritableException`
- `AsyncRequestNotUsableException`

특히 `MethodArgumentTypeMismatchException`은 `@PathVariable Long id`에 문자열이 오거나 enum
파라미터에 없는 값이 오면 발생한다. 예외 메시지에 사용자가 보낸 값이 들어가므로, 알림 억제 키를
`클래스명|메시지`로 잡으면 요청마다 키가 달라져 억제가 무력화되고 맵이 무한히 커진다. 억제 저장소는
크기 상한과 만료가 있어야 한다.

## nginx 설정을 백엔드 레포에 둔다

**결정**: nginx Dockerfile과 배포 스크립트를 백엔드 레포에 유지한다. 프론트 레포로 옮기지 않는다.

**애초에 여기 있던 이유**: IP 화이트리스트 차단이 백엔드에 더 가까운 행위라고 판단해서. 로그인으로
IP 화이트리스트를 없앴으므로(2026-09-26) 이 이유는 사라졌다.

**그래도 안 옮기는 이유**: 진짜 이유가 따로 있었다. 배포 인프라가 여기 있다. `infra/scripts/`,
`docker-compose.yml`, 서버 SSH 시크릿이 전부 백엔드 레포에 있다. nginx를 옮기면 이것들과 시크릿까지
프론트 레포에 복제해야 하고 배포 스택이 둘로 쪼개진다. 지금 불편한 건 `repository_dispatch` 웹훅
하나인데, 그걸 없애려고 배포 인프라를 이중화하는 건 손해다.

정확히 말하면 백엔드 레포가 인프라 레포를 겸하고 있다. 나중에 인프라를 별도 레포로 빼거나 배포
플랫폼을 바꾸게 되면 그때 다시 본다.

## 프론트 배포가 운영에 반영되지 않던 버그

**증상**: 프론트 브랜치를 골라 배포해도 운영 웹이 바뀌지 않았다.

**원인**: 프론트는 정적 자산 이미지를 브랜치 구분 없이 항상 `market-monitor-assets:latest` 하나로만
태그한다. 이 이미지는 런타임이 아니라 백엔드 nginx 이미지를 빌드하는 시점에 박힌다. 그런데 백엔드
`nginx` job에 "`market-monitor-nginx:<태그>`가 이미 있으면 재빌드 스킵" 최적화가 있었고, 이 태그는
최초 1회 빌드 후 항상 존재하므로 그 뒤로는 영원히 재빌드가 스킵됐다. 예전에 박제된 프론트 코드가
계속 재배포되고 있었다.

**조치**: `nginx` job의 스킵 체크를 제거하고 매번 재빌드한다.

정정 — `renderer`도 같은 버그였다. 처음엔 "`application`/`renderer`는 태그가 자기 커밋을
가리키므로 문제없다"고 적었는데, `renderer`는 그렇지 않다. main에서의 태그가 `:latest`
고정이라 nginx와 똑같이 최초 1회 빌드 후 영원히 스킵된다. 그동안 브랜치 시험 배포
(`:branch-<이름>`, 새 브랜치면 태그가 없어서 빌드됨)가 유일한 재빌드 경로 역할을 우연히 하고
있었다. 1A단계에서 `renderer`의 스킵 체크도 함께 제거했다. 자기 커밋 기준이라는 서술이 맞는 것은
`application`뿐이고 그것도 1A 이후로는 빌드 자체를 하지 않는다.

스킵 로직을 고친 것과 이미지가 실제로 갱신되는 것은 별개다. 1A 병합 뒤에도 `target=renderer`를
직접 돌린 적이 없어서, 2026-09-09까지 서버 2에는 8월 하순 브랜치 배포 때 만들어진 이미지가 그대로
떠 있었다. 그동안 렌더러에 들어간 변경(캡처 준비신호 대기 등)이 하나도 나가지 않은 상태였고,
백엔드만 배포하면서 "고쳤는데 왜 그대로지"를 반복할 뻔했다. `application` 배포가 렌더러를 건드리지
않는다는 사실은 `docs/operations.md`에도 적어뒀다.

**더 나은 방법(보류)**: 프론트 자산을 `assets:sha-<프론트커밋>`으로도 태그하고 `client_payload`로 그
sha를 넘겨 `ARG ASSETS_TAG`로 빌드하면, 스킵 최적화가 다시 의미를 갖는다(진짜 같은 커밋일 때만 스킵).
프론트·백엔드 워크플로와 Dockerfile 3곳을 고쳐야 해서 급한 불만 끄고 미뤘다.

아래는 "죽은 코드"가 아니다. 나중에 필요할 가능성 때문에 의도적으로 남긴 것이다.

| 대상 | 사유 |
|---|---|
| `ImageStitcher` | 지금은 안 쓰지만 이미지를 이어붙일 상황이 다시 생길 수 있음 |

억제한다. 사유 주석이 중요한 이유는, 다음에 이 코드를 보는 쪽이 "안 쓰네, 지우자"로 판단하지 않게
하기 위해서다.

반면 `commons-lang3`는 실제 사용처가 0건이라 제거 대상이다.

## 스냅샷 시각은 스케줄러가 한 번 찍어서 전 수집기에 넘긴다

**결정**: `CollectionScheduler`가 시각 하나를 정하고 그 값을 모든 수집기에 인자로 넘긴다. 각 수집기가
저장 시점에 `now()`를 찍지 않는다.

**이유**: 5분 주기 수집 사이클 전체가 완료되기까지 약 1분 30초가 걸린다. 테이블마다 저장 시점의
`now()`를 찍으면 초 단위가 전부 달라져서, "16:05 시점의 시장 상태"라는 기준 자체가 성립하지 않는다.
지수는 16:05:03, 종목가는 16:06:20 식이 되면 나중에 두 테이블을 같은 시점으로 조인할 방법이 없다.

이 구조는 유지한다.

## 종목 배정은 명시적으로 만든 것만 있다 (전 종목 미러를 그만뒀다)

**예전 전제**: "활성 일반주는 반드시 배정 행이 있다." 신규 상장마다 이벤트로 배정 행을 만들어 전 종목을
미러링했고, 조회 경로는 이 전제에 기대 방어 코드가 없었다.

**바꾼 이유**: 사용자별 데이터가 되면서 가입할 때마다 종목 수천 건을 만들고 신규 상장을 전 사용자에게
뿌려야 했다. 그래서 `custom_stock_sector`는 **사용자가 직접 배정한 종목만** 담는다. 가입 직후 0건이다.

**지금 규칙**
- 기본 지도는 `stock_info.industry_id`(업종)로 묶는다. 업종이 없으면 "미분류"
- 커스텀 지도·섹터 집계에는 **배정된 활성 종목만** 들어간다
- 종목 관리 목록은 활성 일반주 전체를 보여주고, 배정·별칭이 있으면 붙인다
- 새 **업종**이 생기면 전 사용자에게 같은 이름의 섹터를 한 번 만든다. 새 **종목**은 배정을 만들지 않는다.
  사용자가 지운 섹터는 되살리지 않는다(전체 재조정 배치 금지)

**접은 선택지**: 미러를 유지하고 가입 시 복사. 가입 비용과 전파 비용이 사용자 수에 비례해서 접었다.


## `SnapshotResponse.snapshotTime`은 실제 데이터 시각으로 통일한다

**문제**: 같은 필드에 서비스마다 다른 의미를 담고 있었다.

| 서비스 | 넣던 값 |
|---|---|
| `MarketQueryService` | 기대 시각 (`CollectionChecker.expectedSnapshotTime()`) |
| `MarketMapQueryService` | 실제 시각 |

`MarketQueryService`는 실제로는 16:05 데이터를 조회해놓고 응답 라벨엔 "지금쯤이면 있어야 할" 16:10을
담았다. 데이터와 라벨이 어긋나고, 지연이 발생해도 화면에는 정상 시각이 찍힌다.

**결정**: `MarketQueryService`도 실제 시각을 담는다. 서비스 간 의미를 통일한다.

정상 상황에서는 두 값이 같으므로 화면 변화가 없고, 수집 중이거나 지연됐을 때만 실제 데이터 시각이
찍힌다. 그게 맞는 동작이다.

**"기대 시각"은 어디로 가나**: 지연을 감지해 화면에 표시하는 기능은 별도로 만든다. 그때
`expectedSnapshotTime`과 `latestSnapshotTime`을 각각의 필드로 내려준다. 설계와 선행 조건은
`docs/backlog.md`의 "데이터 지연 감지" 참고. `CollectionChecker`와 `isHoliday()`는 그 기능을 위해
미리 만들어둔 코드이므로 삭제하지 않는다.

## 삭제 범위는 상수로, 실행 스위치만 프로퍼티로 둔다

스냅샷 정리 배치에서 보존 기간(10일)과 보존 시각(15:30~15:40 구간의 가장 늦은 시각)은 상수이고,
드라이런 여부만 프로퍼티였다. 왜 하나는 상수이고 하나는 프로퍼티인지 물어보게 되는 지점이라 적어둔다.

> 드라이런 스위치는 검증을 마치고 PR #131에서 지웠다(2026-09-26, 실삭제 전환). 보존 정책을 바꿀 때
> 같은 검증이 필요하면 스위치를 잠깐 다시 넣는다.

기준은 그 값이 무엇을 정하느냐다. 보존 기간과 보존 시각은 이 배치가 무엇을 남기고 무엇을
지우는지를 정하는 정책이고, 개발 환경과 운영 환경에서 달라야 할 이유가 없다. 프로퍼티의 존재
이유는 대개 환경별 차이인데 여기엔 그게 없다. 둘은 같은 층위의 값이라 하나만 프로퍼티로 빼면
기준이 흐려진다. 바꾼다면 둘 다 함께 빼는 것이 맞다.

드라이런은 성격이 다르다. 술어를 한 번 검증한 뒤 배포 없이 뒤집어야 해서 프로퍼티로 열었다.
"코드 변경 없이 전환 가능해야 한다"가 애초의 요구였다.

부수적으로, 프로퍼티로 선언하면 환경변수 오버라이드 경로가 자동으로 열린다. 서버 env 파일 한
줄로 삭제 범위가 바뀔 수 있게 되는데, 되돌릴 수 없는 작업에서는 그 경로를 굳이 열어둘 이유가
없다. 다만 이건 부차적인 근거다. `application.properties`에 선언된 값 자체는 레포에 있고 리뷰와
배포를 거치므로, 오타 위험이 상수보다 크지는 않다.

## 대량 insert 배치화를 검토했고 미뤘다

`MarketSnapshotCollector`가 종목당 `save()`를 호출한다. PK가 IDENTITY라 Hibernate 배치가
구조적으로 불가능하다.

**미룬 이유**: 초당 20건 수준이라 장애로 이어지지 않는다(수집 사이클이 1~3초 더 걸리는 정도). 반면
해결하려면 PK를 시퀀스로 바꾸는 마이그레이션이 필요하고 마이그레이션 규칙(선-머지 2단계)을 밟아야
해서 절차가 무겁다. 상세는 `docs/backlog.md`.

## 상장폐지 종목은 토스로 거른다 (2026-10-13)

**배경**: 키움 `ka10099` 응답에는 상장폐지 전용 필드가 없고, 폐지된 종목이 응답에 오래 남는다. 키움이 응답에서 빼기 전까지는 `stock_info`에서도 활성으로 남았다.

**결정**: 종목 정보 동기화(`StockInfoCollector.sync`, 평일 07:00)에서 토스 `GET /api/v1/stocks/all`의 `status=DELISTED` 종목코드(코스피·코스닥)를 받아, 키움 응답에 있어도 응답에 없는 것처럼 다뤄 비활성으로 돌린다. 신규 종목이어도 저장하지 않는다.

- **코드 재사용 방어**: 같은 코드가 `status=ACTIVE`로도 있으면 폐지 목록에서 뺀다. 그래서 시장마다 `DELISTED`와 `ACTIVE`를 둘 다 받는다(4번 호출, 한도가 초당 1회라 호출 사이를 1.1초 띄운다).
- **이상 응답 방어**: 키움 응답 중 토스가 폐지라고 하는 종목이 5%를 넘으면 어느 한쪽 응답이 이상한 것으로 보고 이번에는 거르지 않는다(`log.error`).
- **토스 실패는 동기화를 막지 않는다**: 조회에 실패하면 경고만 남기고 이번에는 거르지 않는다. 키움 동기화는 그대로 진행한다.
- **토큰은 하나를 공유한다**: 토스는 클라이언트당 유효한 토큰이 하나뿐이라 새로 발급하면 이전 토큰이 무효가 된다. 달력 클라이언트와 종목 클라이언트가 `TossTokenManager`를 공유한다.
- **NXT 가능 여부는 이번에 바꾸지 않았다**: 토스의 `nxtSupported`는 쓰지 않고 기존대로 키움 `nxtEnable`과 NEXTRADE 편입 목록을 쓴다.

## 거래정지가 연속 5거래일 이어진 종목은 지도와 평균에서 뺀다 (2026-10-14)

**배경**: 거래정지 종목은 거래가 없어 가격이 안 움직이고 등락률 0%로 평균에 들어간다. 병합·감자처럼 정지가 길게 이어지면 시가총액 가중 평균이 0 쪽으로 끌려간다. 일시적인 정지(하루 이틀)까지 빼면 공식 지수와 어긋난다.

**결정**: 거래정지가 **연속 5거래일**에 이른 날부터 지도(마켓맵)와 평균에서 뺀다. 거래가 재개되면 그날부터 다시 들어간다(가격이 다시 들어오면 되므로 영구 제외가 아니다).

- **5거래일은 우리가 정지를 처음 관측한 날부터 센다.** 관측은 거래일 07:00 동기화 한 번뿐이라, 정지가 장 시작 전부터였으면 5거래일째에, 장중에 시작했으면 그날은 세지 않아 정지 첫날 기준으로 6거래일째에 빠진다. 정지 시작 시각을 정확히 알 수 없고 하루 차이는 평균에 미치는 영향이 작아 그대로 둔다.

- **기록**: 거래일 07:00 종목 정보 동기화 뒤 토스 `GET /api/v1/stocks`의 `koreanMarketDetail.krxTradingSuspended`를 활성 보통주 전체(약 2,700개, 200개씩)에 대해 받아 `stock_trading_suspension`에 기간을 남긴다(`started_on`, 5거래일에 이른 `excluded_from`, 재개된 `ended_on`). 휴장일에는 기록하지 않는다. 거래일 수는 `market_calendar`로 센다.
- **제외 판단은 스냅샷 날짜 기준**: `excluded_from ≤ 날짜 < ended_on`(재개 전이면 끝 없음). 지난 날짜를 볼 때도 그날 기준으로 판단하므로, 정지되기 전 날짜의 지도에서는 그 종목이 그대로 보인다. 기록을 시작하기 전 날짜는 영향이 없다.
- **적용 범위**: 지도·그룹 등 `MarketMapQueryService`의 종목 후보(`filterCandidates`)에서 뺀다. MARKETRY·거래소·내 분류에 모두 같다. 업종 분류 데이터(내 분류, 종목 배정)와 Custom 종목 표는 건드리지 않는다.
- **정지 사유는 알 수 없다**: 토스에는 거래정지 사유 필드가 없다. 그래서 병합·분할·감자로 인한 정지도, 문제가 있는 정지도 같은 규칙으로 정지 기간 동안 빠진다. 정리매매(`liquidationTrading`)는 따로 보지 않는다.
- **토스 조회 실패**: 기록을 하지 않는다(그날 기록이 비어 있어 제외가 이어지지 않을 뿐 다른 동작은 그대로). 다음 거래일에 이어서 기록한다.

## 홈의 안내 틀은 그날 새로 생긴 특수한 종목만 알린다 (2026-10-14)

**결정**: 홈 오른쪽의 안내 틀에는 **그날 새로 생긴 일**만 그날 하루 보여 준다. 거래정지처럼 며칠씩 이어지는 일을 매일 보여 주면 무뎌지기 때문이다. 지금 알리는 종류는 둘이다.

- **거래정지**: 연속 5거래일에 이르러 지도와 평균에서 빠지기 시작한 종목(`stock_trading_suspension.excluded_from`이 그날이고 아직 재개되지 않은 활성 보통주). 사유는 알 수 없어 "빠졌다"는 사실만 알린다.
- **신규 상장**: 그날 `stock_info`에 처음 생긴 활성 종목(주권, 이름에 "스팩"이 들어간 종목 포함, 신주인수권·ELW 제외 — 신규 상장 업종 자동 배정과 같은 대상). 하루에 100개를 넘으면 새 환경의 첫 종목 동기화처럼 한꺼번에 들어온 것으로 보고 알리지 않는다.

**API**: `GET /api/map/notices?date=yyyy-MM-dd`(날짜가 없으면 오늘 KST, 로그인 없이 읽는다). 응답은 `{date, items: [{type, stockCode, stockName, market, baseDate}]}`이고 `type`은 `TRADING_SUSPENSION`·`NEW_LISTING`이다. 수집이나 테이블을 새로 만들지 않고 이미 있는 기록(`stock_trading_suspension`, `stock_info.created_at`)으로 만든다.

**건수 두 개 (2026-10-14)**: 응답에 날짜와 무관한 현황 `recentNewListingCount`(기준일 포함 최근 3개월 신규 상장 수)와 `currentSuspensionCount`(재개되지 않은 활성 보통주 수, 아직 5거래일이 안 돼 지도에서 빠지기 전인 종목 포함)를 더했다. 요청 때 캐시·DB로 계산하므로 별도 배치는 없다. 신규 상장은 `stock_info.created_at`(우리가 처음 수집한 날)으로 세는데, 이 환경은 2026-07-24에 종목이 한꺼번에 들어왔으므로 하루 100개를 넘은 날은 세지 않는다.

**한계**: 그날이 지나면 사라지므로 지난날의 안내를 다시 볼 수 없다. 종목 정보 동기화가 07:00에 한 번이라 그날의 안내는 그 동기화 뒤에 생긴다. 종목 정보 캐시는 동기화 직후 비워진다.

## 로그인과 사용자별 데이터

**결정 (2026-09-26)**: IP 화이트리스트를 Google 로그인으로 바꾸고 사이트를 공개했다. 커스텀 데이터는
전부 사용자별이다.

- **인증**: Google OIDC(PKCE + state) → 우리 서버가 발급하는 JWT. 접근 토큰 15분, 회전형 갱신 토큰(해시로
  저장). 둘 다 `HttpOnly`·`Secure`·`SameSite=Lax` 쿠키라 브라우저 JS가 못 읽는다. 쓰기 요청은 Origin
  검사. 계정 키는 `(issuer, sub)`이고 이메일은 표시용이다(이메일은 바뀔 수 있다)
- **권한 판정은 백엔드**: nginx는 요청 제한만 하고 그대로 넘긴다. "경로가 권한을 뜻하는" 구조
  (`/api/admin/**` = 관리자 IP)를 버렸다. 사용자 데이터는 모든 조회·변경에서 인증 주체의 `userId`로
  범위를 건다. URL로 `userId`를 받지 않는다
- **공개 범위**: 비로그인은 기본 지도·섹터를 본다. 커스텀 모드와 관리 화면은 로그인 팝업
- **텔레그램 캡처**: 렌더러는 로그인하지 않은 브라우저다. 백엔드가 2분짜리 **읽기 전용 캡처 토큰**을
  렌더러에 넘기고, 렌더러는 그 페이지의 같은 출처 `/api/` 요청에만 헤더로 붙인다. 쿠키로 넣지 않는
  이유는 렌더러가 브라우저 컨텍스트를 재사용해서 다음 공개 캡처에 인증이 남기 때문이다. 어느 계정
  화면으로 찍을지는 `OWNER_USER_ID`
- **기존 데이터 이관**: 마이그레이션이 임시 소유자(`999999`)에 묶어 두고, 소유자가 가입한 뒤 한
  트랜잭션 SQL로 옮겼다. 앱이 기존 데이터를 자동으로 "주장"하지 않게 한 것은 가입 순서가 꼬였을 때
  남의 계정에 데이터가 붙는 사고를 막기 위해서다

**기본값은 그 값을 쓰는 쪽이 갖는다**
- 색상 구간 기본값은 **프론트 상수**. 백엔드는 색을 계산에 쓰지 않는다
- 시가총액 구간 기본값은 **백엔드 상수**. 기본 지도의 구간 표시와 텔레그램 캡션이 백엔드에서 계산한다
- 사용자가 저장한 행이 있으면 그 값, 없으면 기본값. **가입할 때 기본값을 복사하지 않는다** — 복사하면
  기본값을 바꿔도 기존 사용자에게 반영되지 않는다
- 접은 선택지: 기본값 테이블(`default_*`). 몇 건 안 되고 거의 안 바뀌는 개발자 결정 값이라, 테이블로
  두면 결국 마이그레이션에 초기값을 적어야 해서 "배포 없이 바꾼다"는 이점이 없었다

**원본 SQL을 남긴 자리**: upsert(`ON CONFLICT`), `INSERT … SELECT`(가입 초기화·전 사용자 업종 전파),
`pg_advisory_xact_lock`(가입과 업종 전파 직렬화), `RETURNING`. QueryDSL(JPQL)에 없는 문법이고, 일괄
처리는 JPA로 바꾸면 사용자 수만큼 INSERT가 나간다. 나머지는 `style.md` 규칙대로 파생 메서드·QueryDSL
